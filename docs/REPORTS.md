# Reports & MIS (P4-02)

Definitions and formulas for the 18 operational reports. The source of truth for each report's SQL,
columns, filters and permission is the backend registry
(`backend/app/modules/reports/registry.py` and `sql.py`). Titles, descriptions, groups and column-label
overrides are configuration (`public.report_definitions`, rule e).

## How the framework works

| Part | Behaviour |
|---|---|
| Catalogue | `GET /api/v1/reports` lists only the reports the caller may run, grouped. |
| Permission | Every report needs `reports.view` **and** its module permission (table below). Export needs `reports.export`. Admin column defaults need `reports.configure`. |
| Scope | The scope of `reports.view` applies per row: `all` = every row; `department` = rows whose *owner* is in the caller's department; `own` = rows whose owner is the caller. Facility-wide reports without a per-row owner (R-07, R-11, R-13, R-14) need scope `all`. |
| Filters | Query parameters named after the filter keys. Unknown, repeated or invalid values → `422 INVALID_REPORT_PARAMS`. Dates are business-timezone dates (`timezone` setting). Text filters match "contains", case-insensitive. |
| Sort / paging | `sort=<column>&dir=asc|desc`, `page`, `page_size` (1–500, default = `page_size` setting). Nulls sort last; ties break on a fixed column. |
| Totals | Computed in SQL over **all** filtered rows (not just the page): `sum`, `avg`, `max`, `count_true` (shown "x of n") or a weighted ratio. |
| Columns | User choice → admin default of the user's earliest-assigned role that has one → report default. |
| Export | `GET /reports/{code}/export?format=csv|xlsx&columns=a,b` streams all filtered rows through a server-side cursor. CSV is UTF-8 with BOM; text cells starting `= + - @` get a leading apostrophe. XLSX is written by openpyxl in write-only mode (typed numbers/dates, frozen header, a "Filters" sheet). Above `report_export_max_rows` (default 100,000) → `422 EXPORT_TOO_LARGE`. |
| Print | `GET /reports/{code}/print` → branding, filters used, generated by/at, up to `report_print_max_rows` (default 2,000) rows with `truncated` flag. The page `#/reports/{code}/print` prints on A4 landscape with page numbers in the page margin. |
| Saved filters | Per user and report, named, at most one default (applied when the report is opened without filters). |

Ageing buckets (R-01, R-08): **0–1** = age ≤ 1 day; **1–3** = 1 < age ≤ 3; **3–7** = 3 < age ≤ 7;
**>7** = age > 7 days. Ages are measured to now (or to clearance for cleared pendencies).

### R-01 Pending work by step & user
One row per step × assignee (user, or role when the task is role-assigned) over `workflow_tasks` with
status `OPEN`. *Open* = count; buckets as above from `created_at`; *Overdue* = `due_at < now`;
*Oldest* = age of the oldest open task. Total *Open* equals the open-task count (tested), and the sum of
the four buckets equals it.

### R-02 GS lifecycle
One row per goods slip. Stage times are the **first** entry into each status from `gs_status_history`
(`rms_reports.gs_stage_times`): Unboxing started (→ UNBOXING), Step-2 complete (→ ITEMIZATION), CSR
decided (leaving CSR_APPROVAL_PENDING), Inspected (→ RM_REVIEW), In process (→ IN_PROCESS), Commercial
(→ COMMERCIAL_RESOLUTION); Party notified = first `party_notifications.sent_at`; Closed = `closed_at`.
Durations (hours): Gate → Step-2; Step-2 → inspected (or CSR decision); inspected/CSR → in process; in
process → commercial; commercial → closed; Lifecycle = closed (or cancelled, or now) − gate. *Days in
status* = now − last status change (open GS only). **The totals row is the average of each stage
duration = stage turnaround averages.**

### R-03 GS register
One row per goods slip with party, state, station, delivery mode, boxes, gate document, category,
status, line count, documented / received / short quantity (Σ over `gs_items`), flags and closure.
Filters: party, state, station, GS date range, category, status.

### R-04 Inward evidence compliance (BR-04, G-02, DEC-03)
Videos = confirmed `UNBOXING_VIDEO` attachments; Document photos = confirmed `DOC_PHOTO`;
*Evidence complete* = videos > 0 **and** (photos > 0 **or** the latest missing-document exception is
`APPROVED`). Gate → Step-2 = Step-2 complete − gate; Step-2 duration = Step-2 complete − unboxing
started.

### R-05 Inspection summary
Graded quantity of **final** inspections, per product category × condition code. *Not allowed* =
quantity whose allowed-status snapshot is `NO`; *Hazard* = quantity whose behaviour snapshot is
`HAZARD`. Labels are the snapshots stored at grading (G-18). Total quantity = Σ allocations of final
inspections (tested).

### R-06 Rejections & hazard register
One row per rejection: condition (label snapshot), quantity, reason, disposition, hazard flag, where the
rejected lot is now (locations with a positive balance) and its scrap disposal status / manifest.

### R-07 Daily container audit compliance (BR-18, DEC-08)
One row per calendar day in the window (default: the last `report_default_window_days` days, at most
366). *Confirmed on time* = status `CONFIRMED`; *Confirmed late* = `LATE`; *Recorded* = an audit day
exists. Containers, counted quantity and sellable packaging are Σ over the day's lines. Over the
dashboard window (30 days ending yesterday) the on-time and late counts equal the dashboard's
(tested).

### R-08 Pendency register & ageing (BR-20, DEC-12)
One row per pendency. Age = (cleared or now) − opened, in days; ageing bucket as above. Open quantity
with `status=OPEN` equals the dashboard "Open pendencies" quantity (tested).

### R-09 Custody transfers & discrepancies (BR-21, G-09)
One row per transfer: sent / counted / accepted = Σ over its lines; *Counted − sent* (negative =
short); *Discrepancy* = status DISCREPANCY or RECONCILED, or any reconciliation record; latest
reconciliation's resolution and status; hours to accept = accepted − initiated.

### R-10 Technician productivity (BR-23, BR-24)
Per technician, for the activity window: batches and pieces allotted (by allotment date); serviced
(received), pieces checked, batteries installed, outcomes good / repaired / non-good / non-sellable and
average turnaround (received − allotted) from technician receiving records (by receiving date).
**Battery replacement % = 100 × batteries installed ÷ pieces checked** (the totals row is the weighted
rate Σ installed ÷ Σ checked).

### R-11 Battery reconciliation (BR-24, G-10, IC-09)
Per battery type, from the stock ledger of battery lots: *Opening* = net movements before the window;
*Received* = RECEIPT; *Adjusted* = net ADJUST; *Consumed* = CONSUME in the window; *Closing* = net
movements up to the end of the window (= opening + received + adjusted − consumed). From receiving
records: pieces checked, replacement entries, batteries installed. **Installed − consumed** must be 0
(*Reconciled*). A row without a battery type carries pieces checked whose battery was OK.

### R-12 Dismantling & parts recovery (BR-27, BR-28)
Recovered quantity per part type × PCB model × PCB supplier × container (and partition), with the
number of dismantling batches and first / last recovery time.

### R-13 Inventory position as on date
Σ stock movements up to the end of the chosen date (business timezone) per lot and location, grouped
by location, custodian (location's custodian user or role), condition class and item. Dispatched,
credited and disposed locations are excluded unless *Include dispatched / credited / disposed* is set.
As on today with that option, the total equals Σ `stock_balances` (tested).

### R-14 Stock reconciliation exceptions (exceptions only)
`rms_reports.stock_reconciliation_exceptions`, the same formulas as `scripts/integrity_check.sql`:

| Check | Expected | Actual |
|---|---|---|
| IC-01 per GS line (categorised GS) | received qty | Σ lot balances in all locations + quantity that left the ledger − quantity that entered from outside |
| IC-02 negative balance | 0 | the balance |
| IC-03 movements vs balance (per lot × location) | Σ movements in − out | stored balance |
| IC-05 rejection movement | rejection qty | its movement's qty on the same line |
| IC-09 batteries | batteries installed | CONSUME qty from BATTERY_STORE (and every receive CONSUME has a record) |

Difference = actual − expected. A healthy ledger returns **no rows** (pgTAP and pytest assert 0 on the
scenario data; an injected balance error shows IC-01 and IC-03).

### R-15 Store issues & dispatches (BR-31, DEC-21, DEC-26)
One row per store issue (to the Main Store) and per replacement dispatch: number, type, date, GS
numbers, from / to locations, lines and Σ quantity, status, who, acknowledgement, transporter, docket /
vehicle and reference document.

### R-16 Credit note register (BR-32…BR-38, G-13, G-14)
One row per credit note / JV: voucher no. and date (CN or JV), type, status, party document, GST portal
result and return, taxable / CGST / SGST / IGST / total, lines and quantity, **rate sources** = distinct
rate-verification references over its lines, lines rate-verified, and the first party notification.
Count and Σ total equal the `credit_notes` table (tested).

### R-17 CN ageing
One row per current RM CN decision that allows a CN (× its non-cancelled CN). *Decision → issue* =
issued − decided; *Issue → notification* = first notification − issued; *Decision → notification* =
(notification or now) − decided (days). Stage: AWAITING_CN, AWAITING_ISSUE, AWAITING_NOTIFICATION,
NOTIFIED; *days in stage* for open stages.

### R-18 User activity & performance
`rms_reports.user_activity_events`: one event per status change (`gs_status_history`), transfer
initiate / accept, technician allot / receive, dismantling completed, store issue, CN issue, party
notification and dispatch. Per user × step × action: count, goods slips touched and handling time.
**Handling time** = how long the item waited for that action: status change → since the previous status
change of the same GS; transfer accept → since initiation; technician receive → since allotment;
dismantling → since the batch was created; CN issue → since the CN draft. Other actions have none. A
user operation that also moves the GS status counts once as STATUS_CHANGE and once as its domain
action.
